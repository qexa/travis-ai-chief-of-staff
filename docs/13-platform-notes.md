# 13 · Platform notes: building TRAVIS on other stacks

The reference targets Vapi because its server-URL model maps cleanly onto Travis Core. The brain (routing, calendar rules, memory, briefing) is platform-independent; only the adapter changes. Platform features change often; confirm details in each platform's current docs.

## What any platform needs to support

| Requirement | Why |
|---|---|
| Custom tools/functions that call your HTTPS endpoint mid-call and read the result back | All 12 tools |
| Caller ID available to your endpoint | VIP recognition |
| Transfer to a number decided at runtime (or at least a fixed list) | Routing |
| End-of-call webhook with transcript/summary | Records + summaries |
| Dynamic variables in the prompt (nice to have) | Time, exec status, greeting |

## Vapi (reference)

- Tools: `type: function` with `server.url` → `POST /vapi/webhook`, message `tool-calls`, respond `{"results":[{"toolCallId","result"}]}`.
- Transfer: `transferCall` tool with empty `destinations` → `transfer-destination-request` → Core returns the number.
- Dynamic assistant: phone number → server URL → `assistant-request` → Core returns `assistantId` + `assistantOverrides.variableValues`.
- Analysis: `analysisPlan` (summary, structured data, success evaluation) arrives in `end-of-call-report`.
- Everything is generated by `scripts/build_voice_config.py` and deployed by `scripts/deploy_vapi.py`.

## Retell AI

- Create "custom functions" pointing to `POST https://<core>/tools/<name>` (the generic endpoint accepts Retell's `{"call": {...}, "args": {...}}` shape and reads `call.from_number` as caller ID). Protect it: set `TRAVIS_ADMIN_TOKEN` and add `Authorization: Bearer <token>` as a custom header, or verify Retell's request signature in `security.py`.
- Transfers: Retell's transfer-call function with a fixed number list (exec, EA, CFO…). Have the prompt pick the destination named by `route_call`'s `transfer_to`. (Less locked-down than Vapi's server-side resolution, since numbers sit in platform config, but the model still doesn't need to say them.)
- Dynamic variables: Retell's inbound webhook can return `retell_llm_dynamic_variables`; return `assistant_variables()` from Core (add a small endpoint).
- Post-call analysis → configure the same summary/structured fields; point the call-ended webhook at a small adapter that reshapes Retell's payload into `process_end_of_call`'s expected fields.

## Votel.ai (and other GoHighLevel-style agency platforms)

These platforms bundle voice agents with a CRM, calendars, pipelines, SMS and workflows. Two ways to build TRAVIS:

**A. Platform-native (fastest, no server).**
- Voice agent with the TRAVIS system prompt (replace `{{variables}}` with the exec's actual details and use the platform's own date/time variables if available).
- Use the platform's native calendar for availability/booking and set the calendar's own rules (hours, buffers, min notice, daily cap) to mirror `calendar:` in the profile.
- Contacts + tags for tiers (`vip`, `inner-circle`, `vendor`, `spam`); workflows on "call ended" to text the exec a summary when tag = vip or priority = high.
- Transfer actions to the exec/EA numbers.
- A daily scheduled workflow for the morning briefing (list of today's appointments + yesterday's call summaries).
- Trade-off: routing rules live in prompts and workflows, which is harder to test and easier to talk around. Keep the discretion rules strict.

**B. Hybrid (recommended for executives).**
- Keep the platform voice agent + phone number + CRM.
- Add "custom action / webhook" steps that call Travis Core's `POST /tools/<name>` for `lookup_caller`, `route_call`, `take_message` and `search_knowledge`, passing the caller's phone and call ID. Everything in `routing.py` then applies unchanged.
- Point the post-call webhook at a small adapter that calls `process_end_of_call`.
- Use Core's Google Calendar backend, or implement `calendar/base.py` against the platform's calendar API.

## Bland AI

Similar pattern to Retell: "custom tools" call HTTP endpoints with the variables you define; use the generic `/tools/<name>` endpoint. Use pathways sparingly; TRAVIS works best as a single well-prompted agent plus server-side routing, not a rigid node graph.

## ElevenLabs Agents (Conversational AI)

- "Server tools" (webhooks) → `/tools/<name>`; pass `system__caller_id` as `caller_phone` and `system__conversation_id` as `call_id` in the tool body.
- Built-in transfer-to-number tool with a configured list.
- Great voice quality out of the box; check telephony integration (Twilio/SIP) for your number.

## Self-hosted (Pipecat or LiveKit Agents)

For full control and lowest per-minute cost at scale:
- Telephony via Twilio Media Streams / SIP trunk → Pipecat pipeline (Deepgram → LLM → ElevenLabs/Cartesia).
- Register the tools as the LLM's function-calling tools and call `travis.tools.run_tool(name, args, CallContext(...))` **in-process**: no webhook at all.
- Transfer via Twilio's `<Dial>` using the number from `transfer_destination(ctx)`.
- You own latency tuning, interruption handling, scaling and uptime. Only worth it past several thousand minutes a month or for strict data-residency needs.

## No-code backend (n8n / Make) instead of Travis Core

Possible for a single executive:
- One webhook workflow per tool (or one with a Switch on tool name); respond in the platform's expected format (for Vapi: `{"results":[{"toolCallId": {{ $json.message.toolCallList[0].id }}, "result": "..."}]}`).
- Store VIPs/rules in a Google Sheet or n8n data table; calendar via the Google Calendar node; SMS via Twilio node; briefing via a Cron node.
- You lose unit tests and deterministic enforcement unless you rebuild the logic carefully. The Python reference is about 2,500 lines; it's usually faster to deploy it than to rebuild it in nodes.
